# Contributing

Keep contributions practical and independently useful: a skill, playbook, pattern, field note or small example with a clear purpose. Add category directories only when real reviewed content needs them. Do not add placeholder articles or claims about unpublished material.

## Change discipline

1. Use a named branch and define the intended behaviour before changing it.
2. Keep one canonical skill body under `skills/`. Keep referenced resources beside it and preserve relative links. Names describe the work rather than a vendor command.
3. Preserve attribution and licence scope. Do not apply MIT to CC-BY-4.0 companions. Retain the complete PRD source map and notices; changes to approved PRD interview/template behaviour need explicit review.
4. Do not include credentials, real client identifiers, private operational exports, website assets, historical workspace artifacts, binary/font files or skill ZIPs. Use synthetic examples labelled as such, not invented case studies presented as evidence.
5. Do not add installers, hooks, telemetry, permission bypasses, global configuration or a native adapter without a separate approved, testable requirement.
6. Report verification actually performed and distinguish local checks from native-host or CI evidence. A maintainer reviews changes before any publication or release.

## Local validation

Use Python 3.10+ in a chosen environment outside the checkout, with PyYAML installed from requirements-test.txt:

```sh
python -m pip install -r requirements-test.txt
python -B -m unittest discover -s tests -v
```

No parser fallback exists; a missing PyYAML dependency is an error. `-B` avoids generated bytecode in this deliberately allowlisted tree. The suite uses the standard-library unittest runner; it makes no network calls or host configuration changes.

Add a failing regression test before fixing behaviour. Confirm the failure is for the intended reason, then make the smallest change and rerun the full suite. If adding a public file or changing an intentionally pinned PRD resource, review the allowlist/fingerprint change explicitly rather than weakening the gate to make it pass.

Before publication, inspect the full Git tree, staged diff and history for unexpected files and sensitive content. Passing pattern checks is not proof that arbitrary text is safe to publish. Native integration claims need their own real host test and current official contract, not only frontmatter checks.
