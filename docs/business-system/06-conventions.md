# Conventions

Rules that bind every skill in the business system, so no skill has to restate them. A skill may narrow these rules. No skill may contradict them.

## Evidence

A claim that something worked needs a reading from the system where the work happened: the revision that deployed, the record that was written, the payment that landed. An assistant's summary is not evidence.

## Authority

Anything that spends money, grants access, commits a date or sends a message to a third party needs a named person's approval, recorded against the exact thing approved. Approval of a class is not approval of an instance.

## State

One owner per object. If two skills could write the same object, the object is defined once and only its owner writes it. Duplicated ownership is how two skills start disagreeing in public.

## Settings

Rates, thresholds, response windows, names, addresses and limits belong to the business, not to the skill. A skill that cannot read a setting stops and says which one is missing. It never assumes a default, because an assumed number is a wrong answer that looks like a right one.

## Unknowns

A missing reading is unknown. Never zero, never a guess, never a smoothed estimate. Unknown is shown as unknown so a person can decide whether it matters.

## Failures

Every skill has one failure path: contain, record, escalate to a named person. Silent retry is not a failure path. A failed check sends the item to a person, not back round the loop until it passes.

## Mechanisms

Judgement belongs in a skill. Determinism belongs in a workflow or a product that holds the arithmetic. A skill that claims to verify its own output is describing a hope.

## Wording

Plain business language. No codes, no host-specific syntax, no vendor commands, nothing a reader would have to translate.
